# Architecture

Kitty Remote has three parts: a desktop agent, a relay, and a web app served by the relay.

```text
phone browser ⇄ HTTPS/WSS ⇄ relay ⇄ outbound WSS ⇄ agent ⇄ Unix socket ⇄ Kitty
```

## Agent

The agent (`src/kitty_remote/agent.py`, `kitty.py`) runs as the desktop user and talks to Kitty only through `kitten @`, always with an explicit socket and window ID. It discovers instances from `--socket`, `--socket-glob`, or `$XDG_RUNTIME_DIR/kitty-remote-*`, and reports each window's title, working directory and size — never environment variables, command lines or foreground processes.

Every target is `device_id + agent_epoch + kitty_instance_id + window_id`. The instance ID is bound to the socket's inode, peer PID and process start time, and each window is tagged with a random user variable. A closed window, a reused ID, a lost tag, a changed instance or an agent restart invalidates the old target, and input for it is rejected.

## Relay

The relay (`src/kitty_remote/relay.py`, `storage.py`) is a single FastAPI process with SQLite. It stores the admin account (Argon2id), browser sessions, paired devices and credential digests, but never terminal text or input. It authenticates browsers by session cookie and agents by device token, checks the `Origin` of browser requests, grants one control lease per window, and routes screen updates, input and receipts.

Connections, leases, rate limits and routing live in memory, so the relay must run as one process without extra workers or replicas.

## Web app

The web app (`web/`) is React and TypeScript. `web/src/screen.ts` parses Kitty's ANSI output into styled rows and computes row diffs; `TerminalView.tsx` replaces only the DOM rows that changed and relies on native scrolling. Character widths come from Kitty's own tables in `web/src/widths.ts`, generated by `scripts/gen_widths.py`. Terminal text is only ever inserted as text nodes. Both the agent and the browser strip OSC, clipboard, hyperlink and other non-display sequences.

## Screen and history

For a subscribed window the agent samples the visible screen every 300 ms, backing off to 2 s when nothing changes, and reads the full buffer about once a second. Buffer updates travel as `buffer_start`, `buffer_chunk` and `buffer_end` messages. Each update names a base version, a row range to replace and the new rows, split into chunks below 1 MiB. Each hop keeps its own base version, and a new or reconnecting browser always receives the full buffer first. History is capped at 16 MiB of UTF-8.

## Input

An input request carries a UUID, the full target, an operation (`text`, `text_enter` or `keys`) and a deadline in relay time, at most 10 s after receipt. The agent converts the deadline using a clock offset measured at connection time, re-validates the target, and executes requests for one window in order. Text is limited to 64 KiB and sent with `send-text --stdin`; keys come from a fixed allowlist.

A repeated request ID with the same payload returns the original receipt; the same ID with a different payload is rejected. Receipts are `received`, `submitted`, `rejected`, `failed` or `uncertain`. `submitted` only means the Kitty call returned. When a connection drops, pending input is reported as `uncertain` and is never resent.

## Pairing

`kitty-remote pair` asks the relay for an 8-character code (valid for 5 minutes) and a separate high-entropy secret. After the admin approves the code in the web app, the agent claims its device token with the secret. The relay keeps only a digest of the token; the agent stores it in a `0600` file. Revoking a device invalidates the token and closes its connections immediately.
